# 架构演进评估（V7.0 批次8）

> 本文档是批次 8 的交付物：对路线图中"常驻 Worker/队列"与"动态贴吧分表合并"两个演进方向给出
> 基于当前代码事实的评估与建议。结论先行：**调度维持 cron + `do.php` 并新增可选常驻循环模式（已落地）；
> 分表暂不合并，给出明确的重新评估触发条件。**

## 一、调度：cron + do.php / 常驻 Worker / 消息队列

### 现状（已具备的机制）

- 触发：系统 crond 或容器 s6 每分钟调用 `do.php`（CLI 带 `--pw` 或 Web 带 `?pw=`）。
- 调度核心：`cron::runall()` 按 `nextrun` 选取到期任务；`runOnce` 单任务执行。
- 可靠性（批次 4）：任务级防重入锁（`GET_LOCK` 语义的 UPDATE + 超时过期恢复）、失败指数退避、
  最大重试后渠道告警去重、`task_runs` 运行历史、结构化日志。
- 扩展点：`cron_1` / `cron_2` 插件钩子包裹整个调度周期。

### 选项对比

| 维度 | A. cron + do.php（现状） | B. 常驻 Worker（`--loop`，本批已落地） | C. 消息队列（Redis/DB 队列） |
| --- | --- | --- | --- |
| 多节点去重 | DB 锁跨节点互斥 ✓ | 同左 ✓ | 队列天然互斥 ✓ |
| 任务延迟 | ≤ 1 分钟（cron 粒度） | ≤ 调度间隔（默认 30s，可调） | 秒级/实时 |
| 新增依赖 | 无 | 无（`--loop` 为 do.php 内置模式） | Redis 扩展或队列组件，破坏"零 Composer 运行时依赖"现状 |
| 运维成本 | 一条 crontab | 一个常驻进程（systemd/s6 直跑） | 队列服务 + 消费者 + 监控 |
| 失败语义 | 退避重试 + 告警 | 同左（同一 runall 路径） | 需重新设计重试/幂等/死信 |
| 适用规模 | 单机、任务数 < 数百 | 单机/少量节点、希望秒级触发 | 多节点、异构生产者、任务路由 |

### 结论与建议

1. 采用 A 为默认路径，B 作为可选模式：`php do.php --pw=密码 --loop[=间隔秒]`（默认 30 秒，上限 600）。
   复用全部既有锁与退避机制，不引入第二套调度语义；无 crond 的 Windows 部署可直接用常驻模式替代计划任务。
2. 队列（C）**暂不引入**。重新评估的触发条件（满足其一）：
   - 出现跨语言/跨系统的任务生产者（当前全部任务由应用自身产生）；
   - 需要任务优先级或秒级延迟语义（当前 `nextrun` + 分钟级触发已满足）；
   - 单节点调度成为实测瓶颈（`runall` 单轮耗时超过触发间隔）。
3. 若引入队列，通过 `cron_1`/`cron_2` 钩子以插件形式对接，不改核心调度。

## 二、动态贴吧分表合并评估

### 现状

- 每用户数据落在 `<前缀><users.t>` 表（默认 `tieba`），站点可配置多张分表（`fb_tables` 白名单）。
- 消费方（真实统计）：`ajax.php`、`api.php`、`setting.php`、`lib/class.misc.php`（签到引擎 DoSign）、
  `lib/globals.php`（TABLE 常量）、`lib/reg.php`、`lib/cron_system_sign.php`、`lib/cron_system_sign_retry.php`、
  `templates/baiduid.php`、`lib/class.SignManager.php`（users.t）等约 10 个文件。
- 防线（批次 5/6）：所有动态表名拼接均经 `safe_table_name()` / `safe_table_names()` 白名单；
  用户级分析数据已从分表迁出至全局表（`sign_history`），跨用户统计不再依赖分表 UNION。

### 合并收益

- 单一 Schema 演进点（新迁移只改一张表）；
- 备份/恢复/统计天然跨用户；
- 移除 `users.t`、`fb_tables`、`getfreetable()` 一整层兼容逻辑。

### 合并成本与风险

- 约 10 个消费方文件需切换到统一表 + 谓词（`uid` / 表来源标记列），读写路由需双读过渡；
- 存量分表数据回填需分批执行（expand/contract），大表迁移有停写窗口；
- **插件 ABI 风险最大**：第三方插件存在直接拼接 `users.t` 表名的用法（旧版 weltolk 系插件即按
  `$i['opt']['core_version']` 分支），合并会破坏其兼容性；
- 备份格式变化：旧 `dataBak` 备份含分表结构，合并后需保留恢复兼容层。

### 数据规模判断

分表为扁平表（`uid`/`pid`/`fid` 均有索引），InnoDB 单表在千万行级前无实测压力；
分表本身解决的是"多用户水平拆分"，而当前站的行数量级（每用户几十~几千行贴吧关注）远未触达。

### 结论与建议

1. **暂不合并**。当前问题域（跨用户统计）已由 `sign_history`/聚合报表绕开，收益不成立，风险集中在插件生态。
2. 重新评估的触发条件（满足其一）：
   - 最大单表行数 > 500 万且出现可量化的慢查询；
   - 需要跨用户实时查询贴吧绑定关系（而非统计快照）；
   - 插件生态完成向正式数据访问接口（Repository 层）迁移。
3. 若决定合并，必须走 expand/contract：新建统一表 → 新代码双写 → 分批回填校验 → 切读 → 观察一个完整周期 → 删除旧表；
   且不可逆的数据转换期间保留旧分表的只读归档备份。
