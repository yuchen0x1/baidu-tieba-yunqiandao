# 07 全球开源对标与产品路线图

- 编制日期：2026-08-05
- 数据说明：GitHub 页面实时核验为 2026-08-05；此前 [04-功能对标分析.xlsx](./04-功能对标分析.xlsx) 使用 GitHub Search API 抓取 708 个仓库、筛选出 132 个有效对标项目。星标数会变化，报告中用于判断生态量级，不作为精确经营数据。
- 结论：当前项目是一个“可部署、可用的百度贴吧自动化 PHP 单体”，但还不是一个具备安全、可观测、可扩展、可商业化能力的平台。真正的升级不是堆更多签到脚本，而是把它改造成“个人账号自动化与任务编排平台”。

## 1. 项目全面分析

### 1.1 技术栈与总体架构

| 层 | 现状 | 评价 |
|------|------|------|
| 后端 | PHP 8.4 + PHP-FPM，无 Composer、无框架、无命名空间 | 运行版本新，工程结构仍是 2015 年前后风格 |
| 前端 | jQuery 3.6.4 + Bootstrap 3.4.1，服务端模板渲染 | 无组件体系、无构建工具、大量内联样式 |
| 数据库 | MariaDB 11.4；核心表 MyISAM；动态用户分表 | 无外键、无事务一致性、无迁移体系 |
| 部署 | Docker Compose V2 + Caddy + s6-overlay + OPcache | 部署基础良好，是当前最大现代化亮点 |
| CI | PHP 语法检查 + Compose 配置校验 | 缺少测试、静态分析、构建产物与发布校验 |
| 调度 | 外部 HTTP/定时器访问 `do.php`，`fsockopen` 伪异步 | 无队列、无持久化执行历史、失败可观测性弱 |
| 插件 | 目录约定 + `addAction/doAction` 钩子 | 有生态雏形，但无清单、签名、沙箱、市场、回滚 |

整体调用链可简化为：

```text
Browser/Cron Trigger
  -> Caddy (gzip, fastcgi, static cache)
  -> index.php / ajax.php / setting.php / do.php
  -> lib: mysql, option, misc, plugins, cron, SignManager
  -> templates/ + source/ + plugins/
  -> MariaDB
  -> Baidu Tieba HTTP/JSON 接口
```

### 1.2 模块划分

- 认证与用户：`lib/globals.php`，角色为 `visitor/user/vip/admin/banned`，登录基于 cookie。
- 配置：`lib/class.option.php` 将 options 缓存进全局 `$i`。
- 签到核心：`lib/class.misc.php`，支持 client/mobile/default/onekey 等模式，TBS 缓存、失败重试。
- 任务调度：`lib/class.cron.php` + `do.php`，`cron` 表记录 name/file/freq/lastdo/log/no/order。
- 插件：`lib/plugins.php`，插件目录 `plugins/<name>/<name>.php` 作为入口，提供 `_callback`、`_show`、`_public` 等约定。
- 工具：`setting.php` 提供用户管理、备份、优化、Run SQL、建表、清表、插件安装。
- 更新：`ajax.php` 从 GitHub 下载 ZIP 后覆盖全站。

### 1.3 数据库设计

- 核心表：`baiduid`、`cron`、`options`、`plugins`、`tieba`、`users`、`users_options`。
- 全部业务核心表为 MyISAM，见 [setup/install.template.sql](./../setup/install.template.sql:14)。没有外键、行锁、崩溃一致性保障。
- `baiduid` 直接以 `text` 保存 BDUSS/STOKEN，属于账号级敏感凭证。
- `users.pw` 使用 `TEXT`，`users.t` 指向动态分表，导致查询、迁移、权限审计都更难。
- 已有新增的 `cron_log_batch`、`baiduid_health`（InnoDB），但 [class.SignManager.php](./../lib/class.SignManager.php:20) 的日志与健康检查未完整接入主签到链路，属于“半成品能力”。
- 缺少：任务执行历史、通知、审计、API 客户端、会话/Token、事件表。

### 1.4 代码质量

- 没有 `composer.json`、PSR-4、命名空间、自动加载和统一异常处理。
- 大量 `global $m,$i`，业务逻辑、数据库访问、模板渲染混合在入口脚本与模板中。
- 大量字符串拼接 SQL，部分用 `addslashes`，缺少 prepared statement 白名单约束。
- [lib/class.P.php:43](./../lib/class.P.php:43) 对数据库中的 `pwdmode` 执行 `eval()`，属于可直接触发远程代码执行的高危设计。
- 无 PHPUnit/集成测试；`upgrade-report` 目录外的 `test.sql` 不是自动化测试。
- 前端无 lint、无类型检查、无构建产物，Bootstrap 3 时代写法为主。
- 代码中已有现代化尝试（`SignManager`、环境变量、健康检查），但链路未闭环，容易让人误以为已完成。

### 1.5 性能瓶颈

- 每个请求加载并缓存大量 options/plugins/users 到全局 `$i`，账号和插件越多，冷启动开销越大。
- MyISAM 表级锁在并发 cron、用户批量刷新、签到状态更新时容易互相阻塞。
- 动态用户分表让聚合统计需要遍历多张表，无法方便做全局看板、分析或分页。
- `do.php` 依赖外部 HTTP 定时触发；任务长、网络慢、PHP 进程被回收时容易丢任务。
- `fsockopen` 伪异步是“尽力而为”，不保证请求完成，也没有幂等与结果回写。
- 静态资源无版本化，仍有空资源请求和大量内联样式；缓存策略已在 Caddy 中部分补齐。
- 本地简单页面 TTFB 很低（约 8ms），说明小规模体验尚可，但上述问题会在账号数、任务数、插件数增长后放大。

### 1.6 安全风险

按风险等级排序：

| 风险 | 证据 | 影响 |
|------|------|------|
| RCE 面 | `eval('return '.option::get('pwdmode').';')` | 数据库或配置被污染后可执行 PHP |
| 凭证泄露 | BDUSS/STOKEN 明文入库 | 账号级凭证泄露，影响远大于密码 |
| 认证脆弱 | cookie 无 session、长有效期 999999、无 HttpOnly/Secure/SameSite 设置 | 可被 XSS/嗅探盗取，难以撤销 |
| SQL 注入 | 大量字符串 SQL + `addslashes`，动态表名缺少白名单 | 数据泄露、篡改、删除 |
| CSRF 薄弱 | [lib/sfc.functions.php:1118](./../lib/sfc.functions.php:1118) 只校验 Referer | 代理、HTTPS、浏览器策略下易失效，也不是标准 Token 机制 |
| 供应链 | [ajax.php:118](./../ajax.php:118) 下载 ZIP 后覆盖全站，无签名、哈希、回滚 | 上游被篡改或误更新即整站损坏 |
| 管理员工具 | [setting.php:196](./../setting.php:196) 提供 Run SQL、DROP/TRUNCATE | 无二次确认、无审计，误操作/恶意操作成本极低 |
| 插件上传 | `ZipArchive->extractTo()` 直接解压 | 需验证路径穿越、文件类型、大小、签名 |
| 明文 HTTP | 多处贴吧接口使用 `http://` | 中间人可截获 Cookie/请求 |
| 安装入口 | 已支持 `install.lock`，但部署默认不自动创建 | 公网裸部署时仍有重装风险 |
| 缺失防护 | 登录无限流、无失败锁定、无审计日志、无 2FA | 暴力破解和入侵溯源困难 |

### 1.7 可扩展性

- 当前是单机、单站点、单体 PHP 应用，适合 1 台服务器、几十到几百用户的小规模部署。
- 无法平滑支持：多节点调度、API 开放、多租户、任务队列、插件市场、企业审计。
- 最大扩展优势是插件钩子和 Docker 化，可以增量演进，不需要 12 个月内全量重写。

### 1.8 核心问题汇总

1. 工程层：无依赖管理、无测试、无迁移、无发布/回滚机制。
2. 安全层：认证、CSRF、SQL、敏感凭证、更新供应链均有明显缺口。
3. 可靠性层：任务无持久化日志、无通知、无可观测性，失败经常静默。
4. 产品层：功能聚焦“贴吧签到”，缺少任务、通知、API、看板、插件市场等平台能力。
5. 市场层：BDUSS 逆向协议脆弱且有合规风险，不能作为长期商业护城河。

### 2.3 对标项目有而本项目没有的能力

1. 可视化任务中心：xxl-job/gocron/Cronicle/Dagu 都有任务列表、运行历史、手动执行、失败重试。
2. 心跳与状态页：Healthchecks/Uptime Kuma 有健康检查、状态页、失败告警。
3. 统一通知：Apprise 覆盖几乎所有通知渠道，ntfy/Gotify 可自托管。
4. API/Webhook：n8n、Activepieces、Healthchecks 都有公开 API，可被外部系统集成。
5. 多平台连接器：dailycheckin/qd 覆盖多个平台，而非只绑定贴吧。
6. 插件生态：WordPress 有清单、版本、更新、权限、主题机制；本项目插件仍是“目录约定 + 文件上传”。
7. 身份与权限：Keycloak 支持 OIDC、SSO、RBAC；当前项目只有 4 个字符串角色。
8. 可观测性：Prometheus/Grafana/VictoriaMetrics 生态成熟；当前项目没有结构化指标。
9. 数据看板：Apache Superset/ECharts/Chart.js 可做签到趋势、账号健康度、成功率。
10. 可视化工作流：n8n/Activepieces/Windmill 提供节点式编排；这是未来差异化方向。
11. AI 工作流：Dify/Flowise/Ollama 可提供 NL 创建任务、失败分类、日志总结，但不适合替代确定性签到逻辑。
12. 企业级能力：SSO、审计、多租户、数据隔离、SLA、合规导出。

### 2.4 值得借鉴的架构设计

- 从 `Sitoi/dailycheckin` 借鉴：连接器/平台适配层、每账号独立配置、结果汇总与失败分级。
- 从 `qd-today/qd` 借鉴：把“HTTP 请求”建模为可编辑任务模板，支持 Cookie、Header、Body、定时执行。
- 从 `healthchecks` 借鉴：任务心跳、周期/宽限期、状态页、API 通知。
- 从 `xxl-job/PowerJob/gocron` 借鉴：任务注册、调度日志、失败重试、手动触发、暂停/启用。
- 从 `n8n/Activepieces` 借鉴：节点图、连接器类型、输入输出 Schema、模板市场。
- 从 `WordPress` 借鉴：插件清单、版本兼容、更新服务器、回滚、权限钩子、生态文档。
- 从 `Keycloak` 借鉴：OIDC、RBAC、2FA、会话管理，不一定要在 V1.1 就引入。
- 从 `Airflow/DolphinScheduler/Temporal` 借鉴：DAG、重试、告警、持久化执行；但本项目 12 个月内应选择轻量方案，避免直接上分布式编排。
- 从 `Vite/esbuild` 借鉴：把前端从散落的 JS/CSS 变成可构建、可缓存、可测试的资源管线。

## 3. 竞品对比分析

### 3.1 维度对比

| 维度 | 本项目现状 | 全球优秀开源项目 | 结论 |
|------|------------|------------------|------|
| 功能完整度 | 贴吧签到、用户、插件、cron、邮件 | dailycheckin 多平台；qd 通用 HTTP 任务；n8n 全流程自动化 | 覆盖面窄，任务/通知/API 是最大差距 |
| 用户体验 | Bootstrap 3，内联样式多，移动端一般 | n8n/Activepieces 可视化；Healthchecks 状态面板；AdminLTE/CoreUI 现代后台 | 需先做任务中心、通知、响应式，再谈视觉 |
| 性能 | 小规模快，但 MyISAM、无队列、无缓存设计 | 主流调度器有队列、持久化、水平扩展 | 单机够用，规模化前先消除表锁和丢任务 |
| 安全 | 存在 eval、明文凭证、Referer CSRF、弱 cookie、无签名更新 | Keycloak、JWT/OAuth2、审计、2FA 是标准 | 当前不可作为公网 SaaS 交付 |
| AI 能力 | 无 | Ollama/vLLM/Dify/Flowise 生态成熟 | 可在 V2 做日志摘要/失败分类，V3 做 NL 任务 |
| 自动化能力 | 有 cron 和重试雏形，但无可视化、无持久化历史 | xxl-job/gocron/Dagu/Healthchecks 成熟 | 这是 0-3 个月必须补齐的核心 |
| 扩展能力 | 插件钩子有雏形，但无市场、签名、沙箱 | WordPress 是最佳生态范式；n8n 有连接器市场 | 插件生态决定能否成为平台 |
| 商业化潜力 | 基本为零，定位过于垂直且合规风险高 | 开源核心 + 托管/企业版 + 市场是常见模型 | 只有转向“个人自动化平台”才有融资故事 |

### 3.3 投资人视角

- 不要把“贴吧签到”写成最终市场：它只是一个高黏性切入场景。真正的市场是“个人数据/账号的自动化管理、任务编排与可信执行”。
- 当前项目从代码层面不具备融资或商业化基础：无审计、无 API、无多租户、无安全体系、无 SLA，商业模式空白。
- 最有价值的部分不是签到协议，而是：可信凭证管理、任务可靠性、通知、API、插件生态、数据自持与审计。
- 需要正视合规风险：BDUSS 等价于账号凭证，自动签到可能违反平台规则；商业化必须以用户授权、透明、可撤回、数据加密、可删除为前提。
- 可行商业模型：开源核心免费自托管；付费托管版、团队版、企业版、插件市场分成；AI 增值功能作为订阅项。

### 4.1 V1.1：快速提升用户体验与可靠性（0-3 个月）

|----------|-----------|----------|--------------|----------|--------|
| 任务中心 | 当前 cron 无日志、无手动触发、失败不可见 | 看到任务状态，失败能重试，不用猜 | 新增 `task_run` 表，封装 `cron::run()`；后台任务列表/手动执行/暂停/重试 | 中 | P0 |

| 凭证加密 | BDUSS/STOKEN 明文存储不可接受 | 即使数据库泄露也不直接泄露账号 | 用 phpseclib + 系统密钥加密，密钥走环境变量/KMS | 中 | P0 |
| InnoDB 与迁移 | MyISAM 无事务/外键，未来必然出事 | 数据更稳，升级可回滚 | Phinx 迁移，逐表转 InnoDB，补充索引和备份验证 | 中 | P0 |

## 6. 未来 12 个月产品路线图

### 6.1 0-3 个月：止血与信任（V1.1）

1. 安全止血：去掉 `eval`，换 Session/Token 认证，CSRF Token，SQL 参数化，登录限流，凭证加密。
2. 可靠性：任务中心、运行日志、手动触发、暂停、重试、失败原因。
3. 通知：Apprise/Server酱/Telegram/Webhook/邮件。
4. 数据库：InnoDB、索引、Phinx 迁移、备份恢复演练。
5. 供应链：签名更新包、更新前备份、失败回滚。
6. 工程基础：Composer、PHPUnit、CI 静态分析、前端 Vite/esbuild。
7. UI：Bootstrap 5/AdminLTE/CoreUI、响应式、暗色模式。

### 6.2 3-6 个月：开放与扩展（V2.0）

1. 队列与 Worker，替代 HTTP cron。
2. REST/OpenAPI、API Key、OAuth2、Webhook。
3. 插件 manifest、签名、版本、回滚，开发者文档。
4. 多平台连接器，至少接入贴吧之外 1-2 个平台。
5. 账号健康、任务统计、状态页、基础指标。
6. RBAC、2FA，可选 Keycloak SSO。
7. i18n 骨架，为海外用户准备。

### 6.3 6-12 个月：平台化与商业化（V3.0）

1. 托管 SaaS 控制平面、多租户、团队、计费。
2. 插件市场、模板市场、开发者分成。
3. 可视化工作流编辑器。
4. AI 助手：NL 创建任务、失败诊断、日报、异常检测。
5. 企业版：SSO、审计、BYOK、数据导出/删除、SLA。
6. 全球部署：i18n、多区域、Kubernetes/Helm、可观测性体系。

### 6.4 必须做、可延期、不要做

**必须做**

- 安全加固：eval、SQL 注入、CSRF、cookie、凭证加密、更新供应链。
- 任务可观测性：日志、重试、手动触发、通知。
- 数据可靠性：InnoDB、迁移、备份、回滚。
- API 与插件规范：这是从工具变成平台的必要条件。
- 自动化测试和 CI：没有测试就不应该继续快速加功能。

**可以延期**

- 2FA/SSO：V2/V3 再做，除非已有企业客户。
- 移动 App：先用响应式 Web/PWA，不急着原生 App。
- 多租户和 SaaS：在单机可靠、API 和插件规范完成后再做。
- 可视化工作流：V3 做，V1.1 先做好任务中心。
- 全球多语言：V2 搭骨架，V3 全面铺开。
- Grafana/Superset 等重型看板：先做轻量页面，有量后再接。

**不要做**

- 不要在 12 个月内做 React/Vue 全量重写；收益低，风险高。
- 不要自研通知聚合；直接用 Apprise/ntfy/Gotify。
- 不要自研分布式调度器；用队列/Dagu/gocron/xxl-job 等成熟方案。
- 不要用 LLM 直接执行签到等确定性操作；AI 只做辅助。
- 不要公开承诺“批量养号/绕过风控/灰色自动化”；会同时毁掉合规性和商业前景。
- 不要无差异地堆平台数量；先做插件/连接器规范，再让生态扩展平台。

## 7. 总体建议

本项目最有价值的资产是：贴吧协议适配经验、插件钩子雏形、Docker 部署基础和社区用户基础。当前最该补的不是“更多签到功能”，而是安全、可靠性、可观测性、API 与插件生态。

建议执行顺序：

1. 先做安全与任务可靠性，它们决定公网部署和商业化的生死。
2. 再做 UI 与任务中心，它们决定用户是否愿意长期使用。
3. 然后做 API、插件规范、连接器，它们决定产品能否从“工具”变成“平台”。
4. 最后做 SaaS、市场、AI、企业版，它们决定商业价值。

在对外表达时，应把产品重新定义为“个人账号自动化与任务编排平台”，把贴吧签到作为第一个场景，而不是全部。
